# Apex PdM: Invariants (what MUST stay, what CAN change)

**Read this before editing ANY firmware, dashboard, script or ML file.**
Last updated: 2026-10-19. Owner: Adam. If a change touches a MUST-STAY item,
STOP and ask Adam in chat first. Do not "fix" it on your own.

How to read the labels:
- **MUST STAY** = changing it breaks data, ML, or the live site. Ask first.
- **CAN CHANGE** = safe, display or convenience only. Go ahead, but follow the checklist at the bottom.
- **UNVERIFIED** = not yet tested on a real wash. Do not assume it works; do not "optimise" it.

---

## 1. Golden rules (apply to everything)

1. **Never delete data.** Move to `archive/` with a line in `archive/ARCHIVE_LOG_*.md`. Do not read or scan `archive/` otherwise.
2. **Never commit secrets.** `.env`, `secrets.h`, tokens, Wi-Fi password, Firebase secret, Tapo credentials stay out of git. Do NOT add hardcoded fallback credentials anywhere (the old `cloud_pdm_sync.yml` has some; they are to be removed, never copied).
3. **Never report hardware or deploy success you did not see.** Say "UNVERIFIED" when it is not confirmed by live data.
4. **Edit the source, not the generated output.** The pages `index.html`, `dashboard.html`, `cloud_dashboard.html`, `historical.html` are generated by `build_clean_dashboard.py`. Edit the build script, rebuild, and keep all four pages consistent.
5. **Code style:** exhaustive inline comments and clear section headers in all code (Adam is a beginner).
6. **No scope creep:** one task = one change set. Do not refactor unrelated code.

## 2. Firmware 07 (`firmware/07_feature_streamer/`)

### MUST STAY (the ML and the dashboard depend on these)
| Item | Value | Why |
|---|---|---|
| Window length | 5.024 s | Every ML feature is per window; changing it changes every feature |
| MPU-6050 sampling | FIFO 200 Hz, 44 Hz DLPF, range ±16 g | Sets the vibration noise floor (~0.033 m/s²) and feature scale; lock before collecting cycles |
| INMP441 | 16 kHz I2S | Spectral features assume this rate |
| Sound scale | `AUDIO_LEGACY_DIV = 1000` (correct scale) | Old firmware 06 was inflated 15.625x; the archiver and ML loader rectify old data only. Never "rescale" new data again |
| Feature definitions | `vib_mag_std` (`sm`), `vib_dom_hz` (`vdf`), `vib_dom_rms` (`vdr`), sound features, power mean | Column meaning must not change once cycles are collected. If you must add a feature, ADD a new one; never redefine an old one |
| Schema | `schema: 3` in `/live` and the session windows | Dashboard and exporter check it |
| `/live` fields | `ax, ay, az, cnt, drops, fw, heap, outbox, power, rms, rssi, schema, session, state, active, ts, uptime, vib_std, vibe` | Dashboard reads these by name. Add new fields freely; never rename or remove existing ones |
| `ax/ay/az` meaning | window MEAN (gravity tilt), NOT vibration | Dynamic vibration is `vib_std` |
| Heartbeat rates | `/live` every 60 s idle, 10 s active | Dashboard online/offline logic (75 s idle tolerance) is tuned to this. If you change the rate, change the dashboard threshold in the same task |
| Session logic | `ACTIVE_POWER_W = 8.0`, `IDLE_TIMEOUT_WINDOWS = 120` (10 min), vib fallback `0.08` | Defines where a wash cycle starts and ends. Changing it changes what a "cycle" is in all training data |
| Upload batching | 6 windows per PATCH, 60 s max age | Firebase quota and write-count design |
| `print=silent`, keep-alive, session gating | as is | Quota and stability |
| Outbox | 48 windows (about 4 min offline) | Was 120, which overflowed RAM by ~11.6 kB. Do not raise it without a RAM check |
| Heap | ~52 kB free steady | Anything that allocates must free; the accel CSV handler uses malloc/free by design |
| Hostnames | mDNS `washer-pdm`, OTA `washer-pdm-rig` | Used for OTA |
| Secrets via `flash_firmware.py` | generated `secrets.h` from `.env` | Never hardcode into the `.ino` |

### CAN CHANGE
- Comments, README text, serial debug prints (keep them short; no per-sample printing).
- Adding NEW `/live` fields (e.g. last two window summaries) as long as RAM stays safe and `drops/outbox` stay 0 in a test.
- `LIVE_ACTIVE_MS` (10 s), only if the dashboard poll logic is updated together.

### UNVERIFIED (do not claim these work)
- A real wash in active mode: session start, END marker, archive step.
- `WHO_AM_I` prints `0x75` instead of `0x68`. Accelerometer data is valid, so treat as a read-address quirk, not a failure. Do not rewrite sensor init because of it.
- `/window.json` and `washer-pdm.local` reachability (needs the rig IP; not in `/live`).

### Flash rules
- Flash only by `flash_firmware.py` (arduino-cli, FQBN `esp32:esp32:esp32:PartitionScheme=min_spiffs`).
- After any flash, verify with live data (uptime climbing, `drops 0`, `outbox 0`, heap stable) before saying "done".
- Do NOT flash during a wash cycle.

### Reference numbers (for sanity checks, from recorded data)

- Idle power 0.5-3 W. Running above 50 W.

## 4. Data and ML (`data/`, `ml/`, `firmware/session_export.py`)

### MUST STAY
- `data/real_sessions/*.csv` are originals. Never overwrite or "clean" in place. Work on copies.
- Legacy rectification stays: `session_export.py` (median > 1200) and `ml/feature_fusion.py` (rms > 2500) fix firmware-06 sound scale. Do not remove, and do not apply them to firmware-07 data.
- ML design: one-class anomaly detection (Mahalanobis with Ledoit-Wolf shrinkage, Isolation Forest, OC-SVM), nested leave-one-cycle-out evaluation, out-of-fold calibration, slow-EWMA cycle verdict. Outputs are anomaly score and cycle verdict only.
- Do not retrain or change thresholds to "make numbers look better". Cycles are few; the false-alarm bound is the rule of three (0 false alarms in n cycles gives ~3/n at 95%: 20 cycles = 14%, 60 = 5%).
- Mixed firmware data: keep firmware version or `phase_source` columns so 06 and 07 can be separated.

### CAN CHANGE
- New analysis scripts, plots, reports (new files, not edits to the originals).
- Adding evaluation of new cycles, as long as the evaluation protocol above is unchanged.

## 6. Change checklist (do ALL of these every time)

1. Re-read this file. Is the change under MUST STAY? If yes, stop and ask.
2. Edit the source file (build script for the site).
3. Dashboard: rebuild all pages, then `node --check` on the extracted script of each page. No syntax errors allowed.
4. Firmware: compile; check RAM; flash; confirm via `/api/live` that `uptime` climbs, `drops 0`, `outbox 0`, heap stable.
5. `git add` (only files you changed), `commit`, `pull --rebase`, `push`. Report the commit hash.
6. Report what you verified and what is UNVERIFIED. Never claim hardware results you did not see.
7. If you changed a MUST STAY item with Adam's approval, update this file in the same commit.
