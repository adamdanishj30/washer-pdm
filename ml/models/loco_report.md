# Leave-one-cycle-out evaluation (nested, healthy baseline + injected faults)

Generated by `py ml/train_unsupervised_pdm.py`. Every number below comes from a model that never saw the cycle it was tested on (threshold and percentile tables included).

## Data caveats

- 8 healthy cycles, 6,461 windows of 5 s; effective sample size for cycle-level claims is 8, not 6,461 (consecutive windows are strongly correlated).
- SmartThings phase labels present on 0% of windows -> the model is NOT phase-conditioned (one pooled model for the whole cycle).
- Power unusable in 5/8 cycles (wash_cycle_2026-10-11_1019, wash_cycle_2026-10-12_1019, wash_cycle_2026-10-15_1020, wash_cycle_2026-10-15_morning, wash_cycle_2026-10-17_0835) -> power features excluded.
- Accelerometer gravity vector moved by up to 0.76 m/s^2 between cycles (sensor re-mounted/tilted) -> only orientation-independent vibration features are used.
- Legacy data = one instantaneous accel sample + one 8 ms audio RMS per 5 s. Impulsive (bearing) and spectral features cannot be computed; collect firmware-07 cycles.

## What these results do and do not show

- They show the false-alarm behaviour on the recorded healthy cycles and how large a sustained, physically-parameterised change must be before the pipeline reliably flags it.
- They do NOT show that real bearing or damper faults would be detected: injected faults are models (see `ml/fault_injection.py` for the limits), and no real fault data exists yet.
- Component labels (acoustic / vibration / power indicators) say where a deviation is, not which part failed. No remaining-useful-life estimate is made: that needs real degradation data.
